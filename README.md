# Pocket Option Signal Bot — v2 (живой поток котировок + анализ ликвидности)

## Что нового в v2 (кратко)

* **Без задержек.** Для каждой пары держится одна постоянная подписка на тики
  (`market_data/live_feed.py`): свечи 1м/5м обновляются в памяти каждым тиком.
  Поток запускается в момент выбора пары, поэтому «📊 Получить сигнал» читает
  готовые 120 свечей по каждому таймфрейму за миллисекунды (раньше каждый
  запрос заново качал историю: до ~27 с). Старшие ТФ (15м/30м/1ч) собираются
  по границам времени (10:00–10:15, а не «каждые 3 свечи»).
* **Новый анализ** (`analysis/structure.py`): снятие ликвидности (равные
  максимумы/минимумы, прокол тенью и возврат), пробой + ретест уровня, ложный
  пробой, отбой, BOS/CHoCH, имбаланс (FVG), импульс/истощение, давление свечей,
  перерастянутость, дивергенция RSI, запас хода до уровня, режим рынка
  (тренд/флэт) — веса факторов разные для тренда и для флэта.
* **Всегда ВВЕРХ/ВНИЗ + вероятность успеха в %** с причинами «за» и «против».
  Процент калибруется по реальным исходам прошлых сигналов (`/stats` показывает,
  сколько реально выигрывают сигналы с оценкой 55%, 60%, 65%…).
* **Экспирации 5–30 сек убраны** (это шум, не анализируемый).
* **Результат сделки** определяется по тику ровно в момент экспирации.
* **Мёртвый SSID больше не прячется**: бот и монитор проверяют, что реально
  приходят котировки, а не только список активов.

## Режим «🧠 Авто — аналитик» (экспирацию подбирает бот)

В меню экспирации первая кнопка — «🧠 Авто». Ручной выбор не изменился: там вы сами
выбираете экспирацию и получаете чистый результат модели.

В режиме «Авто» (`analyst/`, `bot/handlers/analyst_flow.py`):
* модель считает все три тройки таймфреймов (1м·5м·15м, 5м·15м·30м, 15м·30м·1ч);
* **направление** — консенсус: усреднённый логит троек (тройки делят таймфреймы, поэтому
  складывать их нельзя — одни и те же свечи считались бы дважды);
* **экспирация** — из состояния рынка, а не из «какая тройка увереннее»: тренд и вялый рынок →
  дольше, флэт, всплеск волатильности и близкий уровень на пути сделки → короче; выбирается
  только среди троек, согласных с консенсусом;
* в сообщении — причины выбора и предупреждения (расхождение троек, «почти монетка», всплеск
  волатильности, неполная история);
* **Claude** (если задан настоящий `ANTHROPIC_API_KEY=sk-ant-...`) после выдачи сигнала
  дописывает комментарий «старшего аналитика». Он только комментирует и оспаривает: менять
  направление и экспирацию не может. Сигнал уходит сразу, комментарий добавляется правкой
  сообщения; при ошибке или таймауте сообщение просто остаётся без него.

Проверка на истории (`python -m backtest.desk_check`, ~300 тыс. решений): правила аналитика
не вредят и не помогают — winrate 50,0–50,1% во всех вариантах, разница с ручным выбором
+0,06 п.п. [−0,11; +0,24]. Пока у модели нет преимущества, консенсус и выбор экспирации его
не создают; польза режима — последовательность, ясность и честные предупреждения.

Ретест уровня (`analysis/retest.py`): пробой → закрепление → отход → возврат → реакция, с учётом
волатильности и режима рынка; в сообщении — строка «🔁 …».

## Если бот пишет «Pocket Option не присылает котировки»

Сессия (SSID) истекла. Запустите `capture_ssid_windows.bat`, войдите в Pocket
Option в открывшемся окне, новое значение попадёт в `.env` — перезапустите бота.

## Подбор весов на реальных данных (бэктест)

```
.venv\Scripts\python -m backtest.collect --minutes 240   # записать свечи (4 часа)
.venv\Scripts\python -m backtest.run                     # прогнать стратегию, винрейт
.venv\Scripts\python -m backtest.fit_weights             # подобрать веса
```

`fit_weights` обучается на первых 70% истории, проверяет на последних 30% и
сохраняет `analysis/model_weights.json` только если на невиданных данных
стало лучше. Бот подхватывает файл при перезапуске.

# Pocket Option Signal Bot — этап 4 (Claude второе мнение + SQLite-статистика)

## Источник данных

Официального API у Pocket Option нет. Бот подключается к тому же
WebSocket-каналу, что и веб-платформа, через неофициальную библиотеку
[`binaryoptionstoolsv2`](https://pypi.org/project/binaryoptionstoolsv2/)
(реверс-инжиниринг сообщества, не аффилирована с Pocket Option).

Авторизация — не обход капчи/2FA: вы логинитесь в Pocket Option как обычно в
браузере, а значение авторизации либо ловит скрипт из реального сетевого
трафика вашей же сессии, либо вы копируете его вручную через DevTools — в
обоих случаях вставляете в `.env` (см. следующий раздел; способ получения
этого значения менялся по ходу отладки — актуальная версия ниже). Бот
работает от **одного общего аккаунта** (значение `POCKET_OPTION_SSID` в
конфиге) — так решили для простоты; все пользователи бота получают сигналы
по котировкам этого аккаунта.

**Важное уточнение по установленной версии (`binaryoptionstoolsv2==0.2.14`),
проверенное прямо по её исходному коду, а не по её же bundled README (оно в
этой части устарело и противоречит собственному коду пакета):** на текущей
версии сайта Pocket Option браузер **не ставит cookie с именем `ssid`** —
её больше нет. То, что библиотека называет "SSID" — это по-прежнему полная
строка вида `42["auth",{"session":"...","uid":...,"isDemo":0,"platform":1}]`
(это подтверждено чтением `sanitize_and_validate_ssid()` в
`BinaryOptionsToolsV2/pocketoption/asynchronous.py` — она требует ровно два
поля, `session` и `uid`, и не запустит подключение без них).

Про то, откуda конкретно брать значение `session`: в исходниках библиотеки
(`pocketoption/tools/login.py`) её собственный встроенный автоматический
логин берёт его из cookie `po_session` — но на практике эта cookie
существует не у всех аккаунтов/регионов (набор cookies, судя по всему,
отличается по версии/локали сайта). Поэтому это README больше не называет
одну конкретную cookie единственным источником значения — см. следующий
раздел, где основной способ вообще не требует знать имя cookie: он ловит
готовое сообщение авторизации прямо из сетевого трафика вашей же сессии.

**Про поле `uid`:** его не обязательно знать точно. `sanitize_and_validate_ssid()`
только *предупреждает* (не отклоняет подключение), если `uid` отсутствует или
не похож на настоящий — критична только сама пара ключей `session`/`uid` в
JSON, а не конкретное числовое значение `uid`. Более того, встроенная в
библиотеку функция автоматического логина (`pocketoption/tools/login.py`,
функция `login()`) сама всегда подставляет `"uid":0` независимо от реального
аккаунта — это видно прямо в её коде (`return f'42["auth",{{"session":
"{session}","isDemo":{{...}},"uid":0,"platform":2}}]'`). Раз так делает даже
официальный (для этой библиотеки) способ логина — `uid: 0` рабочее значение,
отдельно искать свой настоящий числовой `uid` не нужно.

*(Библиотека также умеет полностью автоматизировать сам логин по email и
паролю — `login()`/`login_async()` в том же файле, с обходом reCAPTCHA через
headless-браузер или платные сервисы вроде CapSolver/2captcha. Я сознательно
не подключаю это к боту и не привожу инструкцию по нему: это автоматизация
входа в реальный аккаунт в обход капчи/защиты от ботов Pocket Option, что
может нарушать условия использования площадки и привести к блокировке
аккаунта — независимо от того, что сама библиотека это умеет. Ниже — только
ручной способ: вы логинитесь в браузере сами, а бот лишь читает уже
существующее значение cookie.)*

Это неофициальный канал: протокол не документирован Pocket Option и может
измениться без предупреждения (у предыдущей версии библиотеки такое уже
было — её архивировали и заменили). Держите SSID в секрете — он даёт полный
доступ к аккаунту.

## Как получить SSID (Windows, пошагово)

Ничего никому отправлять не нужно — вы сами находите значение в браузере и
сами вставляете его в свой локальный файл `.env` на этом же компьютере. Боту
(и мне) вы это значение не показываете.

**Честно про то, почему этот раздел уже дважды менялся.** Сначала здесь была
инструкция про cookie с именем `ssid` (её на текущем сайте нет ни у кого).
Потом — про cookie `po_session` (её тоже нет у части аккаунтов/регионов —
похоже, конкретный набор cookies отличается по региону/версии сайта). Имя
конкретной cookie — это деталь реализации фронтенда Pocket Option, которая
может отличаться и меняться, и библиотека `binaryoptionstoolsv2` её никак не
фиксирует (её собственная `sanitize_and_validate_ssid()` проверяет только
*форму* значения — JSON вида `{"session":...,"uid":...}` — а не то, из какой
именно cookie оно взято, см. `scripts/explain_ssid_requirements.py` ниже,
который показывает вам это прямо из установленного пакета). Поэтому вместо
третьей попытки угадать имя cookie — три инструмента, ни один из которых не
зависит от того, как называется нужная cookie у вас:

- **Способ 1 (рекомендуется): автоматический захват.** Скрипт сам открывает
  окно браузера и ловит нужное значение из настоящего сетевого трафика — вам
  не нужно искать ничего в DevTools вручную.
- **Способ 2: то же самое вручную**, если способ 1 недоступен (например, без
  дополнительной установки Playwright).
- Если ни один из способов не даёт рабочего значения — раздел
  **«Если ничего не подошло: диагностика»** ниже.

### Способ 1 (рекомендуется): автоматический захват

`scripts/capture_ssid_playwright.py` открывает настоящее, видимое окно
Chromium (не headless, без флагов обхода детекта автоматизации) и просто
слушает его сетевой трафик. **Логинитесь в этом окне вы сами** — email,
пароль, капча/2FA — как в обычном браузере; скрипт не трогает форму входа и
не видит пароль. Как только страница отправит кадр авторизации
`42["auth",...]` (то же самое сообщение, которое вы искали бы вручную в
DevTools), скрипт поймает его автоматически, покажет замаскированный
предпросмотр и спросит, записать ли значение в ваш `.env`.

Это не то же самое, что встроенная в библиотеку функция автоматического
логина (`pocketoption/tools/login.py`, `login()`/`login_async()`) — та
самостоятельно вводит email и пароль и умеет решать капчу через
headless-браузер со стелс-флагами или платные сервисы обхода капчи
(CapSolver/2captcha/NoCaptchaAI). Это я сознательно не подключаю и не
рекомендую: это автоматизированный обход капчи и защиты от ботов на входе в
реальный аккаунт, что может нарушать условия использования Pocket Option и
привести к блокировке аккаунта — независимо от того, что сама библиотека это
умеет технически. Способ 1 в этом README — про другое: обычный видимый
браузер, вход делаете вы сами, автоматизирован только просмотр уже
идущего трафика.

Установка (разово, отдельно от основного бота):
```
pip install playwright
playwright install chromium
```
Запуск:
```
capture_ssid_windows.bat
```
или напрямую: `python scripts\capture_ssid_playwright.py`.

### Способ 2: то же самое вручную, через DevTools

Если не хотите ставить Playwright — то же самое можно поймать глазами.
Внимательно к моменту: кадр `42["auth",...]` отправляется один раз, сразу
после установления соединения, поэтому нужно успеть открыть нужную вкладку
DevTools **до** этого момента (или обновить страницу заново с уже открытой
вкладкой).

1. Войдите на `pocketoption.com`, откройте DevTools (**F12**) → вкладка
   **Network** («Сеть»).
2. В строке фильтров типов запросов (All, Fetch/XHR, JS, CSS, Img...)
   нажмите **WS** (WebSocket). Включите **Preserve log** («Сохранять лог»
   в Edge) — так список не очистится при обновлении страницы.
3. **Обновите страницу (F5)** с открытыми DevTools, активным фильтром WS и
   включённым Preserve log — так соединение установится заново у вас на
   глазах. В списке запросов должен появиться один запрос типа WebSocket
   (обычно с именем вроде `websocket`, или адресом, содержащим `socket.io`
   либо цифро-буквенный поддомен). Кликните на него.
   - Если после обновления список всё равно пуст: убедитесь, что фильтр
     стоит именно на **WS**, а не на **All** с последующим поиском глазами;
     попробуйте также полностью закрыть и заново открыть вкладку сайта
     (не просто F5) — иногда WebSocket переиспользует уже открытое
     соединение, которое не пересоздаётся простым обновлением.
4. Откройте вкладку **Messages** (Chrome) / **«Кадры WS»** (Edge) в деталях
   запроса — появится список сообщений с пометкой направления (исходящие от
   браузера обычно отмечены стрелкой вверх).
5. Найдите исходящее сообщение, начинающееся с `42["auth",` (обычно одно из
   первых после установления соединения).
6. Скопируйте его целиком (кликните на строку, чтобы увидеть полностью,
   выделите весь текст и `Ctrl+C`) — оно должно начинаться с `42["auth",` и
   заканчиваться `}]`, без внешних кавычек вокруг всего сообщения.
7. Вставьте в `.env`:
   ```
   POCKET_OPTION_SSID=<вставленное сообщение>
   ```
   без пробелов вокруг `=` и без внешних кавычек вокруг значения.

### Если ничего не подошло: диагностика

Два дополнительных скрипта — на случай, если оба способа выше не сработали,
или чтобы проверить конкретное значение, не редактируя `.env` и не
перезапуская бота каждый раз:

- **`scripts/explain_ssid_requirements.py`** — печатает реальный исходный
  код проверки credential прямо из вашей установленной копии библиотеки
  (`sanitize_and_validate_ssid`), без пересказа с моей стороны — чтобы вы
  сами убедились, что именно она требует (Windows: `explain_ssid_windows.bat`).

- **`scripts/probe_ssid_candidate.py "<значение>"`** — пробует одно
  конкретное значение (например, из любой имеющейся у вас cookie —
  `po_uuid`, `PHPSESSID`, `ci_session`, `autologin`, что угодно) настоящим
  подключением к Pocket Option и честно говорит, принял его сервер или нет.
  Значение никуда не уходит, кроме как напрямую на сервер Pocket Option — тот
  же самый, с которым уже разговаривает ваш браузер. Так вы можете быстро
  проверить несколько кандидатов эмпирически, без переписывания `.env` под
  каждый (Windows: `probe_ssid_windows.bat "<значение>"`).
  ```
  probe_ssid_windows.bat "<значение po_uuid>"
  probe_ssid_windows.bat "<значение PHPSESSID>"
  probe_ssid_windows.bat "<значение ci_session>"
  probe_ssid_windows.bat --demo "<значение autologin>"
  ```
  Если один из них сработает — скрипт покажет готовую строку для `.env`.
  Если ни один — самый надёжный вариант остаётся способ 1/2 выше: значение
  из реального кадра авторизации, а не из cookie как таковой (сервер в
  итоге проверяет именно это сообщение, а не то, из какой cookie вы его
  собрали).

Если Pocket Option через какое-то время начнёт присылать в Telegram-боте
ошибку про SSID (см. следующий раздел) — значит сессия в браузере истекла
или вы вышли из аккаунта; нужно повторить один из способов выше и получить
новое значение (`session` меняется при каждом новом логине).

## Проверка SSID и понятные ошибки

Бот проверяет SSID в двух местах, на двух разных этапах:

1. **При старте, ещё до подключения к сети** (`market_data/ssid.py`,
   подключено к конфигурации в `config.py`) — проверяется *формат*, причём
   так же строго, как это делает сам `PocketOptionAsync` при подключении
   (сверено с его кодом `sanitize_and_validate_ssid()` в установленном
   `binaryoptionstoolsv2==0.2.14`, не придумано заново): пустое значение,
   оставленный плейсхолдер `your_pocket_option_ssid_here`, пробелы/переносы
   строк по краям или таб/перенос внутри значения (частые артефакты
   копирования), значение короче разумного, отсутствие префикса
   `42["auth",`, невалидный JSON после него, JSON не в виде массива из
   `["auth", {...}]`, событие с именем не `"auth"`, данные после него не
   объект, либо отсутствие обязательных полей `session`/`uid` внутри —
   ровно то же самое, что проверяет и сам клиент библиотеки. Мелкую
   проблему (например, потерянные кавычки вокруг `auth` из-за копирования
   через shell) исправляет автоматически, как и сам клиент. Если что-то из
   критичного не так, бот **не запустится** и выведет в консоль конкретную
   причину и что делать — вместо непонятной ошибки где-то в середине
   работы.
2. **При старте, но уже с реальным подключением** (`PocketOptionProvider.
   verify_connection()` в `main.py`, до того как бот начинает отвечать в
   Telegram) — бот один раз реально обращается к Pocket Option. **Важно:**
   эта проверка больше не запрашивает свечи по конкретной паре (раньше был
   жёстко зашит EUR/USD) — она вызывает `active_assets()`, тот же метод
   `PocketOptionAsync`, что и всё остальное здесь, верифицированный по
   исходникам установленного пакета. Это просто список активов с сервера —
   для него не важно, какая именно пара сейчас торгуется, важна только
   валидность самой сессии. Раньше эта проверка ложно писала «SSID неверный»
   по выходным, когда обычный (не OTC) EUR/USD закрыт для торговли, хотя
   сессия была абсолютно рабочей — теперь так быть не может. Если проверка
   всё же не прошла на **самом первом** обращении к Pocket Option за весь
   запуск — это гораздо вероятнее означает, что SSID неверный или истёк
   (протух), чем случайный сетевой сбой, и сообщение об ошибке прямо так и
   говорит, с отсылкой к этому разделу README и к диагностическому скрипту.
   Такая проверка не может отличить «SSID точно верный» от «повезло с сетью
   в этот момент» на 100% (у неофициальной библиотеки нет фиксированной
   иерархии ошибок, чтобы различать причины надёжно) — но она гарантированно
   ловит самый частый случай: протухший/неверный SSID, который иначе давал
   бы непонятную ошибку только при первом нажатии «Получить сигнал» в
   Telegram у случайного пользователя, а не сразу и явно при запуске.

   **Важный технический момент** (если вы видите ошибку `Uninitialized,
   Assets not initialized yet.`): сразу после подключения библиотека ещё не
   успела получить список активов с сервера — для этого у неё есть отдельный
   метод `wait_for_assets()` (тоже верифицированный по исходникам, его же
   вызывает внутри себя `PocketOptionAsync.__aenter__()` — то есть это
   штатный, задокументированный способ дождаться готовности, а не костыль).
   Перед каждым вызовом `active_assets()` — и при `verify_connection()`, и
   при проверке активности пары в `get_candles()` — бот теперь сначала ждёт
   `wait_for_assets()`. Если вы видели эту ошибку — обновите
   `market_data/pocket_option.py` (см. патч ниже) и перезапустите бота.
3. **При каждом запросе свечей для конкретной пары** (`PocketOptionProvider.
   get_candles()`) — перед самим запросом бот тем же способом (`active_assets()`,
   по возможности — если этот вызов сам не удался, проверка просто
   пропускается, не блокируя остальное) сверяет, входит ли запрошенная пара
   в список сейчас активных у Pocket Option. Если нет — вместо непонятной
   `BinaryOptionsError: General("Assets not found")` из самой библиотеки бот
   отвечает понятным сообщением на русском, какая пара недоступна и какие
   из активных сейчас пар доступны (регулярные и OTC вперемешку, если хоть
   одна). См. следующий раздел про то, откуда вообще берётся список пар для
   выбора в боте — он больше не жёстко зашит.

**Отдельный баг самой библиотеки** (если видите `Pocket Option error while
fetching ... 'NoneType' object is not iterable` — для ЛЮБОЙ пары, не только
одной конкретной): в установленном пакете `binaryoptionstoolsv2==0.2.14`
метод `PocketOptionAsync.history()` не имеет реализации — в исходнике только
docstring, ни одной строчки кода после него, поэтому он всегда молча
возвращает `None`. `get_candles_live()` внутри библиотеки объединяет
результат этого метода с двумя другими источниками данных через цикл без
проверки на `None` — и падает с этой ошибкой гарантированно на каждом
вызове, независимо от пары, таймфрейма или того, открыт ли рынок. Это
подтверждено чтением установленных исходников и скриптом
`scripts/debug_get_candles_live.py`. Бот теперь сам подменяет этот сломанный
метод сразу после подключения (`market_data/pocket_option.py`,
`_patch_broken_history_method`) на версию, которая просто возвращает пустой
список — ровно то поведение, которое остальной код библиотеки и так
ожидает от «источника, который не сработал». Если вы видели эту ошибку —
обновите `market_data/pocket_option.py` и перезапустите бота.

Все три случая покрыты тестами (`tests/test_ssid_validation.py`,
`tests/test_config_ssid_validation.py`, и новые тесты в
`tests/test_pocket_option_provider.py` — в т.ч. что проверка активности
пары пропускается, если сама `active_assets()` не отвечает, а не блокирует
всё остальное).

## 24/7 без присмотра: что делать, когда SSID протухнет

Честно, до архитектуры: у Pocket Option нет официального API и нет
refresh-токена — то есть **полностью без участия человека этот канал в
принципе не проживёт бесконечно**, независимо от того, как написан бот. Ни
одна из проверенных мной библиотек (`binaryoptionstoolsv2` и все аналоги —
см. историю переписки) не предлагает способа обойти это; единственная
альтернатива — автоматизированный обход капчи/антибот-защиты при логине по
паролю, который я осознанно не подключаю (см. выше). Поэтому цель ниже — не
«убрать участие человека совсем» (это нереалистично для неофициального
канала), а **свести это участие к минимуму**: бот сам замечает, когда сессия
реально умерла, и явно просит освежить её, вместо того чтобы вы вручную
проверяли это или — хуже — молча получали пустые ответы в Telegram.

### Сколько реально живёт сессия — не гадаем, а измеряем

Никто (ни я, ни исходный код библиотеки) не может сказать заранее, сколько
именно живёт конкретно ваша сессия — это зависит от Pocket Option, а не от
кода. Вместо предположений — измерительный скрипт:

```
monitor_session_lifetime_windows.bat
```

Оставьте его работать (в отдельном окне терминала, или через Планировщик
заданий Windows) сколько угодно — часы, дни. Раз в 5 минут (настраивается
`--interval`) он делает один лёгкий запрос к Pocket Option и построчно
пишет результат и в консоль, и в `session_lifetime_log.csv` (не теряется при
закрытии терминала). Как только сессия действительно умрёт — увидите точное
время первого сбоя и сможете прикинуть реальный интервал обновления SSID
именно для вашего аккаунта, вместо того чтобы полагаться на чьи-то догадки.

### Что бот делает сам, пока работает 24/7

`market_data/session_monitor.py` — фоновая задача (запускается в `main.py`
рядом с резолвером сигналов), которая раз в
`POCKET_OPTION_HEALTH_CHECK_INTERVAL_SECONDS` (по умолчанию 5 минут) делает
такой же лёгкий запрос. Важно: она **не** сигналит на каждый одиночный сбой
— у неофициального канала бывают единичные всплески, которые сами проходят,
и дёргать вас на каждый из них — плохая идея (быстро научит игнорировать
алерты). Сигнал уходит только после
`POCKET_OPTION_HEALTH_CHECK_FAILURE_THRESHOLD` (по умолчанию 3) неудачных
проверок подряд — то есть уже похоже на настоящий обрыв, а не всплеск — и
только один раз за один такой обрыв, плюс одно уведомление о
восстановлении, когда соединение снова заработает.

Куда уходит уведомление — в Telegram, в чат с номером `TELEGRAM_ADMIN_CHAT_ID`
из `.env`. Найти свой `chat_id`: напишите боту `/start` один раз, затем
посмотрите в его логи (консоль/файл лога) — строка вида
`chat_id=123456789 used /start`; сторонний бот для этого не нужен. Если
`TELEGRAM_ADMIN_CHAT_ID` не задан — бот всё равно работает, просто пишет
эти события только в свои логи, без сообщения в Telegram (и предупреждает
об этом один раз в консоли при старте).

Когда алерт всё же придёт — порядок действий тот же, что и раньше:
`capture_ssid_windows.bat` (или ручной способ / `probe_ssid_candidate.py`),
новое значение в `.env`, перезапуск бота. Это ручной шаг «раз в N дней», а
не «постоянный ручной контроль», которого вы опасались изначально.

Логика алертинга (не сами сетевые вызовы) покрыта тестами —
`tests/test_session_monitor.py`: не сигналит ниже порога, ровно один алерт
на затянувшийся обрыв, ровно одно уведомление о восстановлении, повторный
обрыв после восстановления алертит снова, сбой самой отправки в Telegram не
роняет остальную логику.

## Что реализовано на этом этапе

### ⚡ Текущий активный режим: мульти-таймфреймный анализ, взвешенный
### Score/Confidence, WAIT убран снова

**Это по прямому запросу пользователя (2026-09-12): бот больше не должен
отвечать «пропустить»/«сигнала нет» ни при каких обстоятельствах — на выходе
всегда CALL или PUT. Это отменяет предыдущее решение (2026-09-10) разрешить
WAIT — почитайте внимательно, если возвращаетесь к этому проекту позже и не
помните, почему бот ведёт себя именно так.**

Раньше (см. историю решений ниже) бот дважды менял позицию: сперва «всегда
отвечать» (простой равновзвешенный голос, форс через `force_direction`),
потом «честно отвечать WAIT, если индикаторы противоречат друг другу»
(строгое большинство таймфреймов без разногласий). Текущее решение — снова
всегда отвечать, но не откатом к старой грубой логике, а с более качественным
взвешенным анализом внутри: каждый из 7 факторов в `analysis/confirmation.py`
теперь даёт не плоский голос -1/0/+1, а **градуированную оценку** от -1 до +1
(например, у EMA-выравнивания учитывается ширина расхождения EMA9/EMA50
относительно ATR, а не только сам факт, что они выстроены в нужном порядке),
факторы дальше взвешиваются по надёжности (тренд старшего ТФ и EMA-структура
весят больше, чем быстрые осцилляторы вроде Stochastic), и объединяются в одно
взвешенное число — `score` (-1..+1). Его знак — направление, а его модуль в
паре с тем, сколько факторов реально согласны, — это **confidence (0-100%)**,
показываемый в сообщении. Низкая уверенность — это теперь то, как «не
уверен» выражается вместо WAIT: сигнал всё равно выдаётся, но помечен как
слабый.

Текущее поведение:

- **Под выбранную экспирацию бот сам подбирает тройку таймфреймов**
  (`analysis.multi_timeframe.timeframe_trio_for`) и анализирует их все:

  | Экспирация | Тройка таймфреймов |
  |---|---|
  | до 5 минут включительно | M1 → M5 → M15 |
  | до 15 минут включительно | M5 → M15 → M30 |
  | до 1 часа включительно | M15 → M30 → H1 |

  Каждый таймфрейм анализируется через `analyze()` независимо; свечи более
  старшего таймфрейма из той же тройки используются как «тренд старшего ТФ»
  для таймфрейма под ним (M1 смотрит на тренд M5, M5 — на тренд M15, и т.д.)
  — то есть на тройку тратится ровно 3 запроса свечей, не 3×2.
- **Комбинирование тройки — тоже взвешенное, не голосование большинством.**
  `analysis.multi_timeframe.combine_timeframe_results` берёт `score` каждого
  таймфрейма, взвешивает его собственной confidence этого таймфрейма (более
  уверенный таймфрейм значит больше), суммирует — знак суммы и есть итоговое
  направление. Разногласие между таймфреймами больше не даёт WAIT — оно
  просто тянет итоговую confidence к 50%, честно показывая, что таймфреймы
  разошлись, но не отказываясь отвечать. Логика отдельно протестирована в
  `tests/test_multi_timeframe.py`.
- **Бот всегда отвечает 🟢 CALL или 🔴 PUT — WAIT в интерфейсе больше нет.**
  Рядом с направлением всегда показан процент уверенности; ниже 60% в
  сообщении дополнительно появляется предупреждение «⚠️ Слабый сигнал».
  Каждый сигнал (любой confidence) сохраняется в `/stats` как обычный
  CALL/PUT и реально резолвится в WIN/LOSS/UNKNOWN — раньше WAIT сразу
  помечался как `outcome='N/A'` и не резолвился, теперь резолвится всё.
- **Claude-проверка (`ai/review.py`) по-прежнему НЕ подключена** — тоже по
  явному запросу: только технический анализ, без обращения к Claude API
  (это быстрее и не требует `ANTHROPIC_API_KEY`). Модуль полностью рабочий и
  протестированный — чтобы включить его как дополнительный фильтр поверх
  мульти-таймфреймного вердикта, заведите `claude = ClaudeReviewClient(...)`
  в `main.py`, передайте его в `get_signal` и прогоните
  `analyze_multi_timeframe()`-результат через `ai.review.review_signal`
  перед сохранением — см. подробности в разделе «`ai/` — Claude как второе
  мнение» ниже. Учтите: если вы это сделаете, WAIT снова сможет появиться —
  но уже только как решение Claude, а не правило-based движка.
- Экспирация выбирается пользователем и определяет и тройку таймфреймов
  (выше), и насколько сильно дисконтируется confidence (`Expiration.
  is_short` для экспираций короче минуты применяет дополнительный,
  более жёсткий дисконт — см. раздел про `analysis/confirmation.py`).

**Что это значит на практике:** «📊 Получить сигнал» по-прежнему заметно
медленнее, чем старый однотаймфреймный режим (до ~3 раз — по одному запросу
свечей на каждый таймфрейм тройки, строго последовательно, не параллельно —
см. docstring `bot/handlers/signal.py` про то, почему параллельные запросы к
Pocket Option не используются: это осознанный компромисс в пользу
стабильности WebSocket-соединения, не забытая оптимизация). Сама математика
взвешенного скоринга — чистая арифметика поверх уже посчитанных индикаторов,
и практически не добавляет задержки: единственная реальная стоимость — это
сеть, а не анализ.

### ⚡ Новое (2026-09-13): более глубокий price-action / структурный анализ

**Тоже по прямому запросу пользователя.** Явное требование: не дублировать
уже существующий анализ (тренд/свечи/уровни/индикаторы/мульти-таймфрейм), а
сделать его глубже — научить бота учитывать нюансы поведения цены, которые
раньше не считались вообще: состояние рынка (тренд/флэт/импульс/замедление),
пробои уровней и их подтверждение, ретесты, ложные пробои, отскоки от сильных
уровней, повторные тесты S/R, смену структуры рынка, ранние признаки
разворота, силу покупателей/продавцов по поведению свечей, свечные формации и
комбинации, резкие импульсы и их последствия, консолидацию перед пробоем,
реакцию цены на уровни и запаздывающие/слишком поздние входы. Явно
запрещалось добавлять факторы "ради количества" — поэтому все 14
перечисленных пользователем нюансов свёрнуты в **4 составных градуированных
фактора**, а не в 14 отдельных, — каждый закрывает несколько связанных
нюансов сразу, не размывая систему весов конфирмации.

Новый модуль `analysis/structure.py` (`analyze_structure(candles, levels,
indicators) -> StructureResult`) считает:

- **`structure_score`** (-1..+1) — структура рынка по swing high/low
  последних ~40 свечей: растущие вершины и растущие основания — бычья
  структура, падающие — медвежья; смена этого паттерна и есть «смена
  структуры рынка». Дополнительно дисконтируется вдвое, если гистограмма
  MACD в этот момент расходится с направлением структуры (структура вверх,
  но MACD уже вниз) — это и есть «ранний признак разворота» без второго
  прохода по индикаторам.
- **`level_reaction_score`** (-1..+1) — реакция цены на ближайший уровень
  (из уже посчитанных `analysis.support_resistance.find_levels`), с
  приоритетом: ретест-после-пробоя-и-продолжение > ложный пробой (пробили и
  вернулись обратно) > свежий пробой с подтверждением > отскок от уровня >
  нейтрально. Вес уровня растёт с числом его касаний (`Level.touches`) —
  многократно протестированный уровень значит больше, чем разовый.
- **`momentum_score`** (-1..+1) — резкий импульс (диапазон свечи намного
  больше среднего по последним 8, тело доминирует над тенями) против
  затишья/консолидации перед этим — «последствия резкого импульса» и
  «консолидация перед пробоем» одним и тем же расчётом.
- **`candle_pressure_score`** (-1..+1) — давление покупателей/продавцов по
  тому, где закрываются последние 5 свечей относительно своего диапазона
  (не сами формулы индикаторов, а именно поведение цены внутри свечи),
  плюс распознавание пары формаций (звезда/инсайд-бар) как усиливающего
  сигнала.
- **`overextension_penalty`** (0..1, не фактор направления) — насколько
  далеко цена от EMA20 в единицах ATR. Не голосует ни за одну из сторон —
  только дисконтирует итоговую confidence («вход может быть поздним»),
  именно так реализовано требование про «запаздывающие и слишком поздние
  входы»: не запрет сигнала, а честное предупреждение и более осторожная
  confidence.

Всё это считается на **уже полученных** свечах и **уже посчитанных**
уровнях/индикаторах — ни одного нового сетевого запроса, ни одного
повторного прохода по индикаторам. Единственная реальная стоимость анализа
по-прежнему сеть (последовательные запросы свечей к Pocket Option), не
математика — то есть требование «максимально оптимизировать скорость
анализа» выполнено буквально: новый анализ не добавляет задержки вообще.

`summary` (строка на русском) — короткое объяснение, какой из факторов дал
наибольший перевес и в какую сторону, плюс пометка про позднюю растянутость,
если применимо; показывается в сообщении Telegram строкой «🔍 …» и передаётся
Claude в промпт (`ai/prompt.py`), когда этот модуль подключён.

Оба реальных бага, найденных при разработке этого модуля (свечное «плато» из
2-3 баров задваивало обнаружение swing-точки и обнуляло `structure_score`
вне зависимости от настоящего тренда; условие отскока от уровня изначально
проверяло не то, что нужно, и не ловило отбой от сопротивления/поддержки),
закрыты регрессионными тестами в `tests/test_structure.py`.

### Данные (без изменений с прошлого этапа)

### Новое: `analysis/` — rule-based технический анализ

Чистый Python, без pandas/numpy — свечей мало (сотни), в тяжёлых
зависимостях смысла нет.

- `analysis/indicators.py` — EMA 9/20/50, RSI(14, Уайлдер), MACD(12/26/9),
  Stochastic(14,3), ATR(14, Уайлдер) плюс `atr_ratio` (текущий ATR к своему
  недавнему среднему — простая мера волатильности). Считаются только по
  **закрытым** свечам (формирующаяся свеча испортила бы индикаторы
  дребезгом на каждом тике). Нужно минимум 60 закрытых свечей
  (`analysis.indicators.MIN_CANDLES`) — меньше не даёт устояться EMA50/MACD.
- `analysis/support_resistance.py` — уровни по локальным swing high/low за
  последние 60 свечей, близкие уровни схлопываются в один с допуском
  0.5×ATR (масштабируется под волатильность конкретной пары).
- `analysis/price_action.py` — поглощение (engulfing), доджи, молот/падающая
  звезда на последних двух закрытых свечах.
- `analysis/trend.py` — тренд старшего таймфрейма: EMA50 + её наклон на
  свечах старшего ТФ (`Timeframe.higher_timeframe`); при нехватке истории
  честно возвращает `UNKNOWN`, а не гадает.
- `analysis/confirmation.py` — **главная логика скоринга**. Одиннадцать
  факторов — семь исходных (EMA-выравнивание, RSI, MACD, Stochastic, price
  action, тренд старшего ТФ, близость к уровню) плюс четыре из
  `analysis/structure.py` (см. раздел про глубокий структурный анализ выше:
  `structure`, `level_reaction`, `momentum`, `candle_pressure`) — дают не
  плоский голос -1/0/+1, а градуированную оценку от -1 до +1 (например, RSI
  даёт полную ±1 только на 25/75, а не сразу на 45/55; MACD дисконтируется
  вдвое, если гистограмма затухает, а не растёт). Оценки взвешиваются по
  надёжности фактора и складываются в одно число — `score`, знак которого и
  есть направление CALL/PUT (всегда одно из двух — WAIT эта функция больше не
  возвращает):

  | Фактор | Вес |
  |---|---|
  | тренд старшего ТФ | 1.3 |
  | близость к уровню (пробой/ретест/ложный пробой/отскок, `level_reaction`) | 1.2 |
  | EMA-выравнивание | 1.2 |
  | MACD | 1.1 |
  | структура рынка / дивергенция (`structure`) | 1.1 |
  | price action | 1.0 |
  | импульс/консолидация (`momentum`) | 1.0 |
  | близость к уровню (S/R, исходный простой голос) | 0.9 |
  | RSI | 0.8 |
  | давление свечей (`candle_pressure`) | 0.8 |
  | Stochastic | 0.7 |

  **2026-09-13: confidence пересчитан по результатам полного backtest'а**
  (217 932 сигнала, `backtest/`, см. `backtest/results/ОТЧЁТ_*.md`) — старая
  формула («чем больше факторов согласно и чем больше |score| — тем выше
  confidence») оказалась откровенно неверной: согласие именно 4 трендовых
  факторов (`ema_alignment`, `higher_timeframe_trend`, `macd`, `structure`)
  на истории **анти-предсказательно** (62% точности при 0 согласных из 4,
  48% при всех 4 — то есть все дружно "за" обычно означает, что движение уже
  почти закончилось), устойчиво по всем 4 периодам и всем валютным парам.
  А вот сила реакции на уровень (`abs(votes["level_reaction"])`) оказалась
  честно и независимо предсказательной (51% → 54% с ростом силы). Новая
  формула это учитывает: `confidence = 50 + 50 * clamp(0.5·reaction_strength
  − 0.6·crowding, -1, 1)`, где `crowding` — доля из этих 4 факторов,
  согласных с направлением сигнала (0..1). Само направление (`score` →
  `direction`, веса факторов) не менялось — backtest не нашёл в нём перекоса
  (CALL 51.4% / PUT 51.6%, разница в пределах шума).

  Confidence дополнительно дисконтируется в трёх случаях — все три проверены
  тестами (`test_short_expiration_applies_a_bigger_confidence_discount_than_normal`,
  `test_low_volatility_reduces_confidence_but_still_decides`,
  `tests/test_structure.py`):

  | Условие | Эффект на confidence |
  |---|---|
  | низкая волатильность (ATR ratio ниже порога) | ×0.7 от отклонения к 50 |
  | короткая экспирация (`Expiration.is_short`, 5-30 сек) | ещё ×0.65 сверху |
  | растянутость от EMA20 (`overextension_penalty` из `analysis.structure`) | ещё до ×0.4 сверху (было ×0.7 — усилено, backtest нашёл, что даже небольшая растянутость уже коррелирует с падением точности) |

  То есть для коротких и/или тихих и/или уже растянутых экспираций итоговая
  confidence может просесть довольно сильно (дисконты перемножаются), но
  направление при этом никогда не пропадает — раньше на этом месте был
  жёсткий порог, переводивший такие случаи в WAIT. Порог «forced» тоже
  пересчитан: раньше это было `min_agreement` (мало факторов из 11
  согласны), теперь — `max_crowding` (СЛИШКОМ много из этих 4 трендовых
  факторов согласны): 0.75 для обычных экспираций, 0.5 для коротких
  (короткие экспирации сам backtest не покрывает — этот порог перенесён по
  аналогии, не проверен на истории). На backtest'е новый `forced=False`
  даёт ~54% точности, `forced=True` — ~50%: старый флаг (до этого патча)
  был перепутан местами (forced=True был точнее, чем forced=False).
  Подробности и полная методология — `backtest/results/ОТЧЁТ_*.md`.

  **2026-09-14: точечный «реверсивный» бонус.** Дальнейший разбор
  `crowding == 0` нашёл, что это не одна однородная группа: когда все 4
  трендовых фактора просто нейтральны (~1% случаев) — точность 51.2%, на
  уровне базы, никакого преимущества. Но когда хотя бы один из них
  **активно противоречит** выбранному направлению — точность 62.5%
  (n=7458), стабильно 60-64% на всех 6 парах и 61.8-63.6% на всех 4
  периодах истории. Это настоящий контр-трендовый/разворотный режим (не
  просто «тренд ещё не подтверждён»), поэтому confidence теперь даёт ему
  отдельный небольшой бонус (`_REVERSAL_BONUS = 0.20` к `raw`, то есть
  +10 к confidence до остальных дисконтов) именно при `crowding == 0 И
  хотя бы один трендовый фактор против направления` — не просто при
  `crowding == 0`. Величина бонуса выбрана из умеренного диапазона
  (проверено 0.10-0.60), а не подогнана под исторические 62.5%. Полный
  backtest подтвердил, что это не ухудшает результат ни на одном из 4
  периодов и 6 пар (изменения в пределах шума, ±0.06 п.п.) — подробности
  и сравнение с отклонёнными альтернативами (переоценка веса crowding,
  снижение порога `forced`) — `backtest/results/ОТЧЁТ_reversal_bonus.md`.
- `analysis/engine.py` — `analyze(pair, timeframe, expiration, candles,
  higher_timeframe_candles)` связывает всё в один `AnalysisResult`.

Это по-прежнему детерминированная, прозрачная эвристика — без Claude. Роль
Claude на этом этапе описана ниже (`ai/`): он проверяет уже готовый вердикт,
а не заменяет его.

### Новое: `ai/` — Claude как второе мнение, а не замена `confirmation.py`

> ⚠️ **Сейчас не используется живым ботом** — см. раздел «⚡ Текущий активный
> режим» выше. Модуль полностью рабочий и протестированный, просто
> `bot/handlers/signal.py` его больше не вызывает.

Поток (когда этот модуль подключён): `Pocket Option → indicators/analysis →
confirmation.py → ai/review.py → финальный вердикт`. Claude вызывается
**только** через `ai.review.review_signal()`. Начиная с этого этапа
`analysis.multi_timeframe`/`confirmation.py` сам больше никогда не
возвращает WAIT (см. «⚡ Текущий активный режим» выше) — так что если этот
модуль всё-таки подключить, единственный источник WAIT в системе становится
именно Claude: сам факт вызова `review_signal()` больше не гарантирован
условием "движок сказал WAIT — Claude вообще не спрашиваем", это условие
просто никогда не сработает.

Жёсткие правила (не настройки — в коде физически нет ветки, которая делает
что-то другое):

- **Направление не меняется.** Если Claude предлагает противоположное
  направление или собственный WAIT — итог всегда WAIT, а не PUT вместо CALL.
- **Claude может только подтвердить или понизить**, никогда не повысить.
  Даже если Claude согласен с направлением, но его confidence ниже порога —
  понижение до WAIT.
- **Порог confidence зависит от экспирации**: 60% для обычных, **85%** для
  экспираций 5-30 сек (`Expiration.is_short`) — то есть даже после того, как
  `confirmation.py` уже применил свой строгий порог (см. таблицу выше),
  Claude должен быть почти уверен, иначе тоже WAIT. Два независимых фильтра
  друг на друге, оба в сторону осторожности.
- **Сбой Claude (сеть, невалидный ответ) → WAIT**, а не "доверимся
  rule-based вердикту" — отказ безопаснее в сторону "ничего не советовать".
- **Если `ANTHROPIC_API_KEY` не задан** — бот не ломается: сигнал
  показывается и сохраняется как rule-only, с явной пометкой "Claude не
  настроен" в сообщении, вместо тихой подмены поведения.

Файлы: `ai/claude_client.py` (обёртка над `anthropic` SDK, строгий парсинг
ответа Claude в JSON — любая аномалия, включая невалидный `direction` или
`confidence` вне 0-100, это `ClaudeError`, а не угаданное значение),
`ai/prompt.py` (собирает промпт из `AnalysisResult`: все индикаторы, price
action, уровни, тренд старшего ТФ, вердикт и голоса `confirmation.py` — и
прямо формулирует Claude, что он не может повышать/переворачивать сигнал),
`ai/review.py` (вся описанная выше логика решения).

### Новое: `storage/` — SQLite-статистика по каждому сигналу

Каждый показанный пользователю сигнал сохраняется через
`storage.SignalRepository` (async, на `aiosqlite`, чтобы не блокировать event
loop бота): валюта, таймфрейм, экспирация, вердикт `confirmation.py`,
итоговый вердикт, confidence, цена входа, снимок всех индикаторов, время.
Текущий live-режим (`bot/handlers/signal.py`) всегда сохраняет CALL или
PUT — WAIT в этом пути больше не возникает, так что резолвится (см. ниже)
каждый сохранённый сигнал. `storage.repository` по-прежнему умеет отдельно
обработать WAIT (`outcome='N/A'`, резолвить нечего) на случай, если Claude-
проверка (`ai/review.py`) когда-нибудь снова окажется подключена — её
собственная логика понижения до WAIT никуда не делась, просто сейчас не
используется.

После того как выбранная экспирация истекает, фоновая задача
(`storage/resolver.py`, запускается в `main.py` через `asyncio.create_task`
рядом с `dispatcher.start_polling()`, проверяет раз в
`RESOLVER_INTERVAL_SECONDS`) берёт реальную текущую цену пары через тот же
`PocketOptionProvider` и определяет исход:

- **WIN** — цена ушла в сторону сигнала (CALL и цена выросла, или PUT и цена
  упала);
- **LOSS** — в обратную сторону;
- **UNKNOWN** — цена не изменилась вообще, либо не удалось получить цену
  (актив закрыт, сбой сети) — результат никогда не выдумывается.

Команда `/stats` показывает сырые счётчики WIN/LOSS/UNKNOWN/pending по
каждой комбинации **пара + таймфрейм + экспирация** отдельно (например,
`EUR/USD + 5M + 1 мин`). "Таймфрейм" здесь — самый быстрый из автоматически
проанализированных таймфреймов для этого сигнала (см. следующий раздел), не
то, что раньше выбирал пользователь вручную. Никакого процента "точности" не
считается и не показывается — задача этой статистики, как и просили, только
в том, чтобы со временем накопить реальные данные о том, какие комбинации
вообще работают, а не в том, чтобы обещать результат заранее.

### Новое: бот сам выбирает таймфреймы — ручного выбора больше нет

Раньше пользователь перед каждым сигналом должен был вручную выбрать ещё и
таймфрейм (кнопка «⏱ Выбрать таймфрейм»). По запросу — это лишний шаг,
а результат важнее — эта кнопка убрана полностью (`bot/keyboards.py`,
`bot/states.py`, `bot/rendering.py`): теперь выбор ограничен только парой и
экспирацией, а таймфреймы бот подбирает сам.

Как это работает (`analysis/multi_timeframe.py`):

- по выбранной экспирации `timeframe_trio_for()` определяет тройку
  таймфреймов подходящего "масштаба" — например, для экспирации ≤5 мин это
  `M1, M5, M15`, для ≤15 мин — `M5, M15, M30`, для ≤1ч — `M15, M30, H1`
  (короткие экспирации не имеют смысла анализировать по H1, а часовая
  экспирация не выигрывает от шума M1);
- каждый таймфрейм из тройки анализируется через тот же `analyze()`, что и
  раньше, при этом свечи одного таймфрейма из тройки одновременно служат
  "трендом старшего ТФ" для таймфрейма на ступень ниже — то есть на всю
  тройку уходит ровно 3 запроса свечей, а не 5-6;
- три отдельных вердикта сводятся в один взвешенным способом, не простым
  большинством: `combine_timeframe_results` берёт `score` каждого
  таймфрейма, умножает на его собственную confidence и суммирует — знак
  суммы решает направление, а разногласие между таймфреймами (например,
  2 CALL против 1 PUT) тянет итоговую confidence к 50%, а не превращает
  результат в отказ отвечать; если удалось проанализировать не все три
  таймфрейма (например, не хватило истории на одном) — комбинируются те,
  что получилось, и лишь если вообще ни один таймфрейм не удалось
  проанализировать, бот сообщает о нехватке истории;
- этот же сведённый вердикт (а не вердикт одного таймфрейма) идёт дальше в
  `ai.review.review_signal()`, если этот модуль подключить — Claude видит
  вердикты по всем проанализированным таймфреймам и может подтвердить итог
  или понизить его до WAIT, но не выбирает между ними и не может вернуть
  ручной выбор.

### Новое: список валют в 💱 теперь живой — включая все активные OTC-пары

Раньше `domain.CurrencyPair` был жёстко зашитым списком из 7 обычных
(не-OTC) форекс-пар — единственным способом добавить туда что-то ещё было
менять код. По запросу это убрано: `CurrencyPair` — больше не фиксированный
набор значений, а обёртка над строкой (реальным тикером Pocket Option вроде
`EURUSD` или `EURUSD_otc`), и список пар для кнопки «💱 Выбрать валюту»
строится заново при каждом открытии этого меню.

Как это работает (`market_data/pocket_option.py`,
`PocketOptionProvider.list_available_pairs()`):

- бот запрашивает у Pocket Option `active_assets()` — тот же метод, что уже
  использовался для проверки «эта пара сейчас торгуется?» — и берёт оттуда
  **все** активные сейчас символы, обычные и `_otc` вперемешку, а не
  заранее заданный список;
- из них оставляются только те, что похожи на валютную пару (6 латинских
  букв, опционально с суффиксом `_otc`) — `active_assets()` вперемешку с
  форексом отдаёт и крипту/индексы/акции, а анализ бота (`analysis/`)
  писался и проверялся только на форекс-подобном поведении цены, так что
  показывать их значило бы обещать то, что бот на самом деле не умеет;
- результат кэшируется на 5 минут (`_PAIR_LIST_CACHE_SECONDS`), чтобы
  каждое открытие меню не было отдельным сетевым запросом к Pocket Option;
- если сам запрос `active_assets()` не удался, или живых валютных пар в
  ответе не нашлось вообще — меню не остаётся пустым: бот показывает
  прежний фиксированный список из 7 обычных пар (`domain.REGULAR_PAIRS`) как
  резервный вариант;
- в меню обычные и OTC-пары показаны двумя подписанными группами («—
  Обычные —» / «— OTC (круглосуточно) —»), чтобы сразу было видно, где что.

OTC-пары у Pocket Option торгуются кругло­суточно, включая выходные (по
собственным, синтетическим ценам Pocket Option, а не реального рынка — это
особенность самого брокера, не бота), поэтому именно на них можно получать
сигналы тогда, когда обычный форекс закрыт. Аналитика, мульти-таймфреймный
анализ и проверка Claude работают для OTC-пар точно так же, как и для
обычных — разница только в списке доступных таймфреймов/пар, не в логике.

**Важно про уже сохранённую статистику:** раньше в SQLite пара сохранялась
как отображаемая метка (например, `EUR/USD`), теперь — как реальный тикер
(`EURUSD`). Старые записи в `/stats` никуда не денутся и по-прежнему будут
показываться под старой меткой, но группироваться со свежими сигналами по
той же паре они больше не будут (это просто смена формата ключа группировки,
не потеря данных).

### Что `bot/handlers/signal.py` делает прямо сейчас (актуальное поведение)

> Описание ниже — то, что реально выполняется при нажатии «📊 Получить
> сигнал» в текущей версии (мульти-таймфреймный режим, см. «⚡ Текущий
> активный режим» в начале файла).

1. по тройке таймфреймов, подобранной под выбранную экспирацию
   (`analysis.multi_timeframe.timeframe_trio_for`), тянет свечи —
   **по одному запросу на таймфрейм, строго последовательно**; если запрос
   по одному таймфрейму не удался (пара закрыта, сбой сети) — остальные всё
   равно пробуются, этот один просто выпадает из голосования;
2. прогоняет каждый успешно полученный таймфрейм через `analyze()` (взвешенный
   скоринг — см. «⚡ Текущий активный режим») и сводит вердикты через
   `analyze_multi_timeframe()` → **всегда CALL или PUT**, с итоговой
   confidence 0-100%;
3. Claude не вызывается — сведённый вердикт идёт в сообщение и в SQLite как
   есть;
4. сохраняет сигнал через `SignalRepository.save_signal()`
   (`claude_consulted=False`, `confidence=` посчитанная rule-based
   уверенность, а не `None` — проверки со стороны Claude в этом режиме нет,
   но собственная confidence движка теперь всегда сохраняется);
5. показывает результат: 🟢 CALL / 🔴 PUT с процентом уверенности (и
   предупреждением, если он ниже 60%), сколько из проверенных таймфреймов
   согласны, сам список таймфреймов, цену входа (по самому быстрому из
   проанализированных таймфреймов), ближайшие support/resistance и строку
   «🔍 …» с кратким объяснением структурного анализа (`StructureResult.
   summary` из `analysis/structure.py` — какой фактор дал наибольший перевес
   и в какую сторону, с пометкой про позднюю растянутость входа, если
   применимо);
6. если не удалось получить свечи вообще ни по одному таймфрейму тройки, или
   ни по одному не хватило истории для анализа — понятное сообщение с
   просьбой попробовать ещё раз чуть позже, а не падение с трейсбеком.

Сделки бот по-прежнему не открывает — ни автоматически, ни как опция. Это
генератор сигналов; решение о том, торговать по конкретному ответу или нет
(особенно при низкой confidence), остаётся полностью за вами — бот в любом
случае не блокирует и не советует за вас.

**Почему «📊 Получить сигнал» отвечает не мгновенно.** В отличие от кнопок
меню (выбор пары/экспирации — это просто локальное состояние, без обращения
к Pocket Option), эта кнопка реально идёт за свежими котировками на сервер
Pocket Option по неофициальному (обратно раскрученному) WebSocket-соединению
— официального API у Pocket Option нет.
Несколько секунд ожидания здесь — это нормально, а не зависание бота: сама
библиотека делает несколько последовательных сетевых запросов на КАЖДЫЙ
таймфрейм (у каждого свой таймаут в 3 секунды), и если соединение идёт через
VPN/прокси (см. «Фоновый запуск без cmd и без ручного VPN» выше), задержка
на каждом таком запросе будет заметнее. `_MIN_BACKFILL_HOURS` в
`market_data/pocket_option.py` (0.75 часа с запасом, не 2 — см. комментарий
там же) не даёт запрашивать больше исторических данных, чем реально нужно.

С переходом на мульти-таймфреймный режим (см. «⚡ Текущий активный режим»)
«Получить сигнал» стало ожидаемо медленнее, чем в прошлом «быстром» режиме —
теперь это до 3 таких запросов подряд (по одному на каждый таймфрейм
тройки, см. `bot/handlers/signal.py`), а не один. Это сознательный выбор в
пользу точности, не регресс. Если конкретный запрос всё равно выглядит
зависшим намного дольше обычного (скажем, больше минуты) — это уже повод
присылать `bot_error.log` для диагностики, а не ждать дальше.

### Windows

обязательно отметить «Add python.exe to PATH»).

Автоматически — двойным щелчком или из `cmd.exe`:

```bat

```

Скрипт создаёт `.venv`, ставит зависимости и копирует `.env.example` в
`.env`, если его ещё нет. После этого откройте `.env` и впишите токены.

Вручную (эквивалент того, что делает скрипт), из `cmd.exe`:

```bat
py -3.11 -m venv .venv
.venv\Scripts\activate.bat
pip install -r requirements.txt
copy .env.example .env
```

В PowerShell команда активации другая (`.venv\Scripts\Activate.ps1`); если
PowerShell блокирует выполнение скрипта политикой безопасности, проще всего
использовать `cmd.exe` (`activate.bat`) — так делает и `setup_windows.bat`.

`binaryoptionstoolsv2` (клиент Pocket Option) ставится из готового wheel —
для Windows на PyPI есть отдельный `win_amd64`-wheel (проверено по списку
файлов пакета), компилятор Rust/Visual Studio не нужен. Если при импорте
всё же появится ошибка загрузки DLL — почти наверняка не хватает
[Microsoft Visual C++ Redistributable](https://learn.microsoft.com/cpp/windows/latest-supported-vc-redist).

Для запуска на Windows `main.py` и `scripts/check_pocket_option_connection.py`
сами переключают event loop на `WindowsSelectorEventLoopPolicy` — иначе
`ProactorEventLoop` (используется по умолчанию) при остановке бота печатает
безобидные, но шумные предупреждения от aiohttp про незакрытые SSL-транспорты
(это рекомендация из документации самого aiohttp для таких случаев). На
Linux/macOS это переключение не выполняется — там оно не нужно.

В `.env` обязательны:

- `TELEGRAM_BOT_TOKEN` — от [@BotFather](https://t.me/BotFather).
- `POCKET_OPTION_SSID` — см. инструкцию в `.env.example` (DevTools → Cookies).

Необязательно:

- `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` — в текущем режиме
  (см. «⚡ Текущий активный режим») бот их не использует вообще, Claude не
  вызывается. Можно не заполнять; модули `ai/*` никуда не делись, если
  захотите вернуть проверку Claude позже.
- `DATABASE_PATH` (по умолчанию `signals.db`) и `RESOLVER_INTERVAL_SECONDS`
  (по умолчанию `15`) — настройки SQLite-статистики (см. `storage/`).
- `TELEGRAM_PROXY_URL` — только если Telegram у вас заблокирован на уровне
  сети (как в Кыргызстане) и без VPN бот не сможет достучаться до Telegram.
  См. «Работа без ручного VPN и без cmd» ниже — с этим настроенным один раз,
  открывать VPN-приложение вручную больше не придётся никогда.

### Фоновый запуск без cmd и без ручного VPN

Если раньше вы каждый раз вручную открывали VPN-приложение, потом `cmd.exe`,
и не хотели, чтобы окно консоли торчало на экране — вот что это заменяет.
Настраивается один раз, дальше — просто ярлык.

#### Шаг 1 (только если Telegram у вас заблокирован в сети, как в Кыргызстане): один раз настроить Cloudflare WARP в режиме прокси

Обычное («полноэкранное») WARP-приложение — это то, что вы сейчас открываете
и жмёте Connect вручную каждый раз. Есть другой режим — **Proxy Mode**:
WARP работает как фоновая служба Windows (`Cloudflare WARP`), которая
запускается сама при включении компьютера и держит соединение сама, без
иконки в трее и без единого клика. Она не заворачивает весь трафик
компьютера — только то, что вы сами направите через локальный
SOCKS5-прокси, который она поднимает. Настроить (один раз, из `cmd.exe`
или PowerShell, с установленным WARP-клиентом):

```bat
warp-cli mode proxy
warp-cli connect
```

Проверить, что прокси поднялся — по умолчанию `127.0.0.1:40000`. Затем в
`.env` укажите:

```
TELEGRAM_PROXY_URL=socks5://127.0.0.1:40000
```

Дальше бот сам подключается к Telegram через этот прокси при каждом
запуске — VPN-приложение открывать не нужно вообще, ни разу. Через этот
прокси идёт **только** соединение бота с Telegram — Pocket Option и
TwelveData как ходили напрямую, так и ходят (см. `config.py:
telegram_proxy_url`). Если Telegram у вас не заблокирован — этот шаг не
нужен, оставьте `TELEGRAM_PROXY_URL` пустым.

#### Шаг 2: запуск и остановка одним двойным щелчком, без окна консоли

Три файла в корне проекта:

- **`start_bot.vbs`** — двойной клик запускает бота полностью в фоне: ни
  одного окна на экране, даже мигающего. Показывает одно окошко-подтверждение
  и всё. Если в `.env` указан `TELEGRAM_ADMIN_CHAT_ID`, в Telegram придёт
  сообщение «✅ PocketSignalBot запущен и готов к работе» в тот момент, когда
  бот реально поднялся — это и есть замена «увидеть строчку в консоли».
  Повторный двойной клик, пока бот уже работает, ничего не сломает — просто
  ничего не сделает.
- **`bot_status.vbs`** — двойной клик показывает окошко: работает бот
  сейчас или нет.
- **`stop_bot.bat`** — двойной клик останавливает бота (окно консоли
  мелькнёт и закроется само).

Если что-то пошло не так и бот падает — `start_bot.vbs` перезапускает его
автоматически (с паузой, увеличивающейся при повторных падениях подряд,
чтобы не долбить Pocket Option/Telegram в тесном цикле), а весь ход событий
пишется в три файла (все — обычный текст, открываются блокнотом, `cmd.exe`
не нужен): `bot_launcher.log` — история самого лаунчера (перезапуски, коды
выхода, не перезаписывается при рестарте), `bot.log` — стандартный вывод
бота, `bot_error.log` — его же ошибки (там же, например, ищется
`chat_id=...` при первой настройке `TELEGRAM_ADMIN_CHAT_ID`, см. «24/7 без
присмотра» выше).

Это не служба Windows и не переживает выключение компьютера само по
себе — при следующем включении нужен ещё один клик по `start_bot.vbs` (по
вашему запросу — именно кнопка, а не полный автозапуск при загрузке
Windows; последнее тоже можно добавить через Планировщик заданий, если
позже захотите).

### «Работает с любого устройства» — что это на самом деле значит

Telegram не запускает бота сам, когда вы открываете приложение — кнопка
«Start» в чате с ботом (она уже есть, это стандартное поведение Telegram)
просто отправляет `/start` уже работающему боту. Отвечает бот с любого
вашего устройства (телефон, другой компьютер, планшет) **уже сейчас, без
доп. настройки** — Telegram сам доставляет сообщение туда, где крутится
бот, независимо от того, с какого устройства вы написали.

Единственное условие — сам процесс бота должен быть жив и подключён к
интернету в этот момент. Пока вы держите бота на своём Windows-компьютере
(сервер — по вашему решению, позже), это значит: **компьютер должен быть
включён и не в спящем режиме**. Два нюанса, которые из-за этого стоит
учесть:

- **Сон/гибернация.** По умолчанию Windows сама уходит в сон через
  какое-то время простоя (и у ноутбуков — при закрытии крышки), и тогда
  бот перестаёт отвечать, пока компьютер не проснётся. Разово решается
  скриптом:
  ```bat
  keep_pc_awake_windows.bat
  ```
  Отключает автосон (от сети и от батареи) и, если это ноутбук — усыпление
  при закрытии крышки. Экран может гаснуть по таймеру как раньше — на
  бота это не влияет, важен только сам системный сон. Отменить позже —
  обычные настройки Windows (Параметры → Система → Питание и спящий
  режим).
- **Выход из системы — не то же самое, что блокировка экрана.**
  Заблокировать компьютер (`Win+L`) — можно, бот продолжит работать в
  фоне. А вот «Выйти из системы» (Sign out) или перезагрузка завершают
  процесс вместе с сессией — тогда снова нужен клик по `start_bot.vbs`
  после следующего входа.

  чем на обычной (и что низкая волатильность тоже снижает confidence, а не
  переводит в WAIT), что направление всегда CALL/PUT (даже на полностью
  нейтральных данных — через tiebreak), и что градуированные оценки
  (EMA-выравнивание, MACD) реагируют на силу, а не только на знак.
- `tests/test_engine.py` — `analyze()` целиком на синтетических свечах.
- `tests/test_signal_handler.py` — обновлён под новый вывод бота (проверяет
  саму проводку: правильные пара/таймфрейм/старший ТФ уходят в провайдер,
  ошибки и нехватка истории показываются понятным текстом); точное
  направление сигнала тут не проверяется — это зона ответственности
  `test_confirmation.py`.

Все эти тесты работают на синтетических/замоканных данных — сеть и реальный
SSID не нужны.

## Проверка вручную с реальным SSID (обязательно перед тем, как доверять сигналам)

Linux/macOS:

```bash
python scripts/check_pocket_option_connection.py [ПАРА] [ТАЙМФРЕЙМ] [КОЛ-ВО]
# например:
python scripts/check_pocket_option_connection.py EUR_USD M5
```

Windows:

```bat
check_pocket_option_windows.bat EUR_USD M5
```

Это отдельный скрипт, не часть pytest — ему нужен настоящий
`POCKET_OPTION_SSID` в `.env` и живая сеть, что не место в автоматических
тестах. Он подключается, тянет последние свечи и печатает их, отдельно
помечая ту, что ещё формируется, плюс отставание последней свечи от
текущего времени. Сверьте это с графиком в браузере Pocket Option:

1. цены (O/H/L/C) последних свечей должны совпадать с графиком;
2. если последняя строка помечена «ФОРМИРУЕТСЯ СЕЙЧАС» — её close должен
   быть близок к текущей цене на графике прямо сейчас;
3. отставание в пару секунд — нормально; если стабильно больше — это и
   есть реальная задержка канала, и её обязательно нужно учитывать при
   решении, использовать ли экспирации 5-30 секунд всерьёз (см. предыдущий
   этап — там это уже разбиралось как открытый риск).

## Не обещаем точность и прибыльность

Ни `confirmation.py`, ни `/stats` не claim-ят предсказательную точность.
`/stats` показывает только сырые счётчики WIN/LOSS/UNKNOWN, накопленные по
реальным исходам — цель в том, чтобы по этим данным понять, какие
комбинации пара+таймфрейм+экспирация вообще из себя что-то представляют, а
какие нет.

**Никакой процент проходимости (70%, 80% — любой) не может быть обещан
кодом** — это было бы утверждение о реальном поведении рынка, а не о
программе. Текущий режим (см. «⚡ Текущий активный режим» в начале файла) по
явному запросу всегда отвечает CALL или PUT — WAIT в интерфейсе больше нет.
Показанный рядом с направлением процент **confidence** — это единственный
способ, которым бот теперь честно говорит "не уверен": число ниже 60%
(с явным предупреждением «⚠️ Слабый сигнал» в сообщении) означает то же
самое, что раньше означал WAIT — тонкие или противоречивые данные — просто
теперь направление всё равно выдаётся, потому что об этом прямо попросили.
Сам по себе высокий confidence тоже ничего не гарантирует — это оценка
согласованности индикаторов между собой, а не вероятность выигрыша сделки;
следите за реальными `/stats`, а не считайте, что раз число высокое, то и
исход предрешён. Очень короткие экспирации (5-30 сек) в принципе одни из
самых шумных и труднопредсказуемых в бинарных опционах — это ограничение
самого инструмента и рынка, а не конкретной реализации бота, и confidence
на них дисконтируется сильнее всего именно поэтому (см. таблицу дисконтов
выше).

## Что дальше (следующие этапы)

1. Автоматическое открытие сделок по-прежнему не реализовано и не
   планируется без отдельного явного решения — бот остаётся генератором
   сигналов.
2. Накопление статистики: сейчас есть вся инфраструктура (`/stats`,
   `storage.get_stats()`), но самих данных пока нет — они появятся по мере
   использования бота. Через какое-то время имеет смысл посмотреть на
   реальные `/stats` и решить, не стоит ли донастроить пороги
   `analysis.confirmation`/`ai.review` под то, что показывают цифры.
3. Резолвер сейчас берёт одну "текущую" котировку сразу после истечения
   экспирации — если задержка канала (см. предыдущий этап) окажется
   существенной, может понадобиться более аккуратная привязка к цене именно
   на момент истечения, а не к моменту опроса.
4. По запросу пользователя идёт переделка интерфейса в несколько шагов
   (сделано: авто-выбор таймфреймов и короткое сообщение с результатом;
   живой список валют с OTC-парами — см. разделы выше). Осталось:
   - более быстрое переключение валют в меню — сократить количество нажатий
     между сменой пары и получением сигнала.
